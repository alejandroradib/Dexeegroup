## Decisions

1. **`npm run db:verify` replaces Docker for CI.** The Supabase CLI local stack needs Docker, which CI runners and this build environment lack. `scripts/verify-migrations.ts` boots PGlite, stubs the `auth` and `storage` schemas and roles, applies every migration, loads `seed.sql` and the JSON banks, asserts RLS on every table and runs the 81-check access matrix (`npm run db:verify`) in `scripts/lib/rls-matrix.ts`. `npm run rls:test` runs the same matrix against a linked project through PostgREST with throwaway users.
2. **`current_user_role()` instead of `current_role()`.** `current_role` is a reserved word in Postgres; the function the spec calls `current_role()` is named `current_user_role()`.
3. **`assessment_questions_public` is a security definer view.** The spec asks for security invoker, but a column-level grant that hides `answer_key` from `authenticated` would also hide it from admins (who are `authenticated`). A definer view with no candidate policy on the base table keeps keys server-side and admin access intact.
4. **Database types are generated locally.** `scripts/gen-types-local.ts` emits `src/types/database.ts` from the PGlite schema in the same shape as `supabase gen types`. `npm run db:types` overwrites it once a project is linked.
5. **Publish guard skips the service role and admins.** `jobs_before_write` raises `company_not_verified` only when `auth.uid()` is set and the user is not an admin, so admins can publish jobs of pending companies and seeds run cleanly.
6. **Guard triggers back the RLS matrix.** Column-level restrictions the spec expresses in prose (candidates can only withdraw, companies cannot set `contact_released`, users can only mark notifications read, candidates cannot set their own English levels) are enforced by `BEFORE UPDATE` triggers, since RLS cannot express per-column rules.
7. **`cooldown_waived` on attempts.** Implements "Reject resets the cooldown" without deleting the attempt: rejected attempts stop counting toward the 90-day rule.
8. **Brand palette from the Dexee brand kit.** Navy `#011842`, green `#02AA86` (accent only, never small text), deep green `#007A61` for links, graphite, slate, mist and mint. Fonts Montserrat (headings) and Inter (body) served locally from the kit under OFL.
9. **Consent version is a code constant.** `CONSENT_VERSION` in `src/lib/legal.ts`, shown on the sign-up form and stored in `candidates.data_consent_version`.
10. **`candidate_cards` includes `desired_salary_min_usd`.** Salary expectation is not contact data and companies need it to shortlist.
11. **Company onboarding stores `hiring_needs` jsonb and profiles store `notification_prefs` jsonb**, as described in SPEC 10.2.
12. **Sentry is behind `SENTRY_DSN` but the SDK is not installed yet.** The build stays free of the `withSentryConfig` wrapper until an org and project exist; `src/lib/logger.ts` (pino) covers structured logs meanwhile.
13. **Email digests dedupe in the outbox.** `email_outbox.dedupe_key` (`new-application:{job}:{user}:{hour}`) implements "at most one new-application email per job per hour".
14. **Legacy peer dependencies.** `.npmrc` sets `legacy-peer-deps=true` because `@react-email/components` pins peers behind React 19.2.
15. **Admin invites reuse `handle_new_user`.** `inviteUserByEmail` creates the auth user; the action then upserts the profile with role `admin`. Deactivation bans the auth user for 100 years rather than deleting history.
16. **IPIP-50 attribution.** Items in `supabase/seed/ipip50.json` are the public-domain 50-item IPIP Big-Five factor markers from ipip.ori.org. SJT items and all English content are original.
17. **MVP document incorporations (2026-09-18).** From the earlier "MVP Dexee Platform" document we adopted four items the spec did not cover: (a) an AI practice interview for candidates (`mock_interviews` table, six bilingual questions per role family, Anthropic grading into a 0-20 report; one open interview per candidate, 30-day cooldown, no effect on matching or on what companies see); (b) granular sign-up consents stored in `candidates.consent_flags` (terms and data policy are required; job contact and aggregated analytics are optional and editable from settings); (c) candidate country of residence from a fixed LatAm list with an admin filter; (d) a free-tools adoption panel on the admin dashboard. Not adopted: DISC (the spec chose IPIP Big Five), the collaborator payroll portal (Phase 2 of the MVP document) and the MVP's alternative pipeline stage names.
18. **Consent metadata is jsonb, not columns.** `consent_flags` keeps `{ terms, data_policy, job_contact, analytics, version }` so future consents do not need a migration; `data_consent_version` stays as the authoritative column for the accepted policy version.
19. **Local demo stack without Docker.** `npm run demo` (see `docs/DEMO.md`) boots a Postgres 16 server, PostgREST and a small gateway that emulates the Supabase Auth, REST and Storage endpoints the app uses, and writes `.env.demo`. It exists so the app can be exercised end to end in environments that cannot reach Supabase or run Docker. It is not a substitute for `supabase start` or the hosted project: storage policies are not exercised and refresh tokens are not rotated.
20. **Nav icons cross the server/client boundary by name.** `RoleShell` (server) passes icon keys and `AppShell` (client) maps them to lucide components, since component functions cannot be serialized into client props.
21. **Function grants are revoked from PUBLIC.** Migration `20260918000002_function_grants.sql` revokes EXECUTE from `public` and `anon` on every security definer function and from `authenticated` on trigger functions, following the Supabase linter (0028/0029), and pins `search_path` on the CEFR helpers (0011). The two security definer views (`public_jobs`, `assessment_questions_public`) stay as designed and are expected to be flagged by lint 0010. Remaining linter items, all performance only, are logged for a later pass: wrap `auth.uid()` in `(select auth.uid())` in policies (0003), the admin catch-all plus role policy pattern (0006) and unindexed audit foreign keys (0001).
22. **Cron schedules are daily while Vercel runs on the Hobby plan.** SPEC asks for `process-attempts` and `process-outbox` every five minutes; Hobby allows one run per day per cron, so `vercel.json` schedules them at 05:00 and 06:00 UTC (retention stays at 04:00). Consequences until the project moves to Pro: oral-assessment grading and outbound email digests can wait up to 24 hours, and the failed-interview retry is only manual. Restore `*/5 * * * *` on both entries when the plan changes; nothing else depends on the interval.
23. **Published prices are provisional and anchored to the market, not to cost.** `src/content/pricing.ts` carries four figures (placement USD 3,500 with a USD 500 deposit, Dexee EOR USD 599 per person per month, managed staffing from USD 4,500 per person per month, Dexee Verified USD 149 per candidate), each marked `provisional: true` with the public competitor pricing it was anchored to in `marketAnchor`. The alternative, hiding prices behind a quote, was rejected: PHASES-GTM 9.1 requires a visitor to state Dexee's price without contacting sales, and a quote-only page is the single most common reason a buyer leaves. The page says the prices are provisional and that a signed client keeps the price they signed. Clear `provisional` and update the table in `docs/CLAIMS.md` once Alejandro sets the final numbers against Dexee's own costs.
24. **Guarantee terms are published as a reviewed-pending draft.** `/guarantee` states the replacement window (90 days, 120 for founding clients), the claim window, the response and shortlist commitments, five exclusions and the remedy, all from `GUARANTEE` in `src/content/pricing.ts`. Publishing terms a buyer's counsel can read before a call is worth more than keeping them in a contract nobody sees, but the page carries a notice that Dexee's counsel has not reviewed them and that the signed contract governs. The notice comes off only after that review; the checklist in `docs/CLAIMS.md` tracks it.
25. **The cost calculator computes the visitor's assumptions, not Dexee's measurements.** `src/lib/pricing/calculator.ts` is pure and runs in the browser; nothing is stored or sent. Every input, including the US and Colombian employer load percentages, is editable and the defaults are labelled as assumptions on the page. This keeps the calculator inside the claim-integrity rule from 9.0: the output is arithmetic on figures the visitor controls, so it makes no claim Dexee would have to source.
26. **`CALENDLY_URL` is optional and its buttons disappear without it.** The variable used to default to an invented URL. It is now `optionalString`, and `BookCallButton` returns `null` when it is unset, so no page ships a booking button that leads nowhere. Set the real link before the domain switch or leave the buttons off.
27. **The sample verification report is a worked example, not an anonymized real one.** PHASES-GTM 9.2 asks for a real, anonymized report. Dexee has not yet run a candidate through the platform, so there is nothing to anonymize; inventing one and presenting it as real would break the rule from 9.0. `/sample-report` renders `src/content/sample-report.ts` and says on the page that the figures were written to show the layout. The structure mirrors the product: the four oral rubric dimensions from `src/lib/assessments/english-oral.ts`, the CEFR scale from `cefr.ts` and the five IPIP factors from `workstyle.ts`. Phase 10.4 replaces the page with the product's own renderer over real seed data; delete `sample-report.ts` then rather than letting the two drift.
28. **Third-party evidence is stored once and rendered from messages.** `EVIDENCE` in `src/content/proof.ts` holds the id, publisher, date, link and the verbatim English statement; the text a visitor reads comes from `marketing.verify.evidence.<id>` so the Spanish page is in Spanish, as rule 4 of CLAUDE.md requires. `tests/unit/proof.test.ts` asserts the English message equals the record in `proof.ts` character for character, and that the Spanish message differs from it, so neither a reworded translation nor an untranslated copy passes the build.
29. **The marketing nav moves to the `xl` breakpoint and drops About.** Adding pricing and how-we-verify made seven top-level items, which pushed the logo out of the bar below 1280px. The six buyer-path links stay in the header from `xl` up and in the sheet menu below it; About keeps its footer link. The logo is `shrink-0` so a longer nav can never collapse it again.
30. **The buyer FAQ moves to semantic message keys and its own section.** `faq1Q`..`faq5A` are replaced by `marketing.companies.faq.<id>.{q,a}` with eleven entries, covering the nine topics PHASES-GTM 9.3 lists plus contact release and English verification. Numbered keys made it impossible to reorder or remove a question without renumbering the rest. The accordion moves out of the two-column pricing block into a full-width section, and `src/lib/seo/faq-page.ts` builds the `FAQPage` JSON-LD from the same strings the accordion renders, because Google drops the rich result when the markup and the visible page disagree. `tests/unit/faq-jsonld.test.ts` enforces the nine-question minimum, the 80-word limit per answer and key parity between locales.
