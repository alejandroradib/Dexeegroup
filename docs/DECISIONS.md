## Decisions

1. **`npm run db:verify` replaces Docker for CI.** The Supabase CLI local stack needs Docker, which CI runners and this build environment lack. `scripts/verify-migrations.ts` boots PGlite, stubs the `auth` and `storage` schemas and roles, applies every migration, loads `seed.sql` and the JSON banks, asserts RLS on every table and runs the 81-check access matrix (`npm run db:verify`) in `scripts/lib/rls-matrix.ts`. `npm run rls:test` runs the same matrix against a linked project through PostgREST with throwaway users.
2. **`current_user_role()` instead of `current_role()`.** `current_role` is a reserved word in Postgres; the function the spec calls `current_role()` is named `current_user_role()`.
3. **`assessment_questions_public` is a security definer view.** The spec asks for security invoker, but a column-level grant that hides `answer_key` from `authenticated` would also hide it from admins (who are `authenticated`). A definer view with no candidate policy on the base table keeps keys server-side and admin access intact.
4. **Database types are generated locally.** `scripts/gen-types-local.ts` emits `src/types/database.ts` from the PGlite schema in the same shape as `supabase gen types`. `npm run db:types` overwrites it once a project is linked.
5. **Publish guard skips the service role and admins.** `jobs_before_write` raises `company_not_verified` only when `auth.uid()` is set and the user is not an admin, so admins can publish jobs of pending companies and seeds run cleanly.
6. **Guard triggers back the RLS matrix.** Column-level restrictions the spec expresses in prose (candidates can only withdraw, companies cannot set `contact_released`, users can only mark notifications read, candidates cannot set their own English levels) are enforced by `BEFORE UPDATE` triggers, since RLS cannot express per-column rules.
7. **`cooldown_waived` on attempts.** Implements "Reject resets the cooldown" without deleting the attempt: rejected attempts stop counting toward the 90-day rule.
8. **Brand palette from the Dexee brand kit.** Navy `#011842`, green `#02AA86` (accent only, never small text), deep green `#007A61` for links, graphite, slate, mist and mint. Fonts Montserrat (headings) and Inter (body) served locally from the kit under OFL.
9. **Consent version is a code constant.** `CONSENT_VERSION` in `src/lib/legal.ts`, shown on the sign-up form and stored in `candidates.data_consent_version`.
10. **`candidate_cards` includes `desired_salary_min_usd`.** Salary expectation is not contact data and companies need it to shortlist.
11. **Company onboarding stores `hiring_needs` jsonb and profiles store `notification_prefs` jsonb**, as described in SPEC 10.2.
12. **Sentry is behind `SENTRY_DSN` but the SDK is not installed yet.** The build stays free of the `withSentryConfig` wrapper until an org and project exist; `src/lib/logger.ts` (pino) covers structured logs meanwhile.
13. **Email digests dedupe in the outbox.** `email_outbox.dedupe_key` (`new-application:{job}:{user}:{hour}`) implements "at most one new-application email per job per hour".
14. **Legacy peer dependencies.** `.npmrc` sets `legacy-peer-deps=true` because `@react-email/components` pins peers behind React 19.2.
15. **Admin invites reuse `handle_new_user`.** `inviteUserByEmail` creates the auth user; the action then upserts the profile with role `admin`. Deactivation bans the auth user for 100 years rather than deleting history.
16. **IPIP-50 attribution.** Items in `supabase/seed/ipip50.json` are the public-domain 50-item IPIP Big-Five factor markers from ipip.ori.org. SJT items and all English content are original.
17. **MVP document incorporations (2026-09-18).** From the earlier "MVP Dexee Platform" document we adopted four items the spec did not cover: (a) an AI practice interview for candidates (`mock_interviews` table, six bilingual questions per role family, Anthropic grading into a 0-20 report; one open interview per candidate, 30-day cooldown, no effect on matching or on what companies see); (b) granular sign-up consents stored in `candidates.consent_flags` (terms and data policy are required; job contact and aggregated analytics are optional and editable from settings); (c) candidate country of residence from a fixed LatAm list with an admin filter; (d) a free-tools adoption panel on the admin dashboard. Not adopted: DISC (the spec chose IPIP Big Five), the collaborator payroll portal (Phase 2 of the MVP document) and the MVP's alternative pipeline stage names.
18. **Consent metadata is jsonb, not columns.** `consent_flags` keeps `{ terms, data_policy, job_contact, analytics, version }` so future consents do not need a migration; `data_consent_version` stays as the authoritative column for the accepted policy version.
19. **Local demo stack without Docker.** `npm run demo` (see `docs/DEMO.md`) boots a Postgres 16 server, PostgREST and a small gateway that emulates the Supabase Auth, REST and Storage endpoints the app uses, and writes `.env.demo`. It exists so the app can be exercised end to end in environments that cannot reach Supabase or run Docker. It is not a substitute for `supabase start` or the hosted project: storage policies are not exercised and refresh tokens are not rotated.
20. **Nav icons cross the server/client boundary by name.** `RoleShell` (server) passes icon keys and `AppShell` (client) maps them to lucide components, since component functions cannot be serialized into client props.
21. **Function grants are revoked from PUBLIC.** Migration `20260918000002_function_grants.sql` revokes EXECUTE from `public` and `anon` on every security definer function and from `authenticated` on trigger functions, following the Supabase linter (0028/0029), and pins `search_path` on the CEFR helpers (0011). The two security definer views (`public_jobs`, `assessment_questions_public`) stay as designed and are expected to be flagged by lint 0010. Remaining linter items, all performance only, are logged for a later pass: wrap `auth.uid()` in `(select auth.uid())` in policies (0003), the admin catch-all plus role policy pattern (0006) and unindexed audit foreign keys (0001).
22. **Cron schedules are daily while Vercel runs on the Hobby plan.** SPEC asks for `process-attempts` and `process-outbox` every five minutes; Hobby allows one run per day per cron, so `vercel.json` schedules them at 05:00 and 06:00 UTC (retention stays at 04:00). Consequences until the project moves to Pro: oral-assessment grading and outbound email digests can wait up to 24 hours, and the failed-interview retry is only manual. Restore `*/5 * * * *` on both entries when the plan changes; nothing else depends on the interval.
23. **Published prices are provisional and anchored to the market, not to cost.** `src/content/pricing.ts` carries four figures (placement USD 3,500 with a USD 500 deposit, Dexee EOR USD 599 per person per month, managed staffing from USD 4,500 per person per month, Dexee Verified USD 149 per candidate), each marked `provisional: true` with the public competitor pricing it was anchored to in `marketAnchor`. The alternative, hiding prices behind a quote, was rejected: PHASES-GTM 9.1 requires a visitor to state Dexee's price without contacting sales, and a quote-only page is the single most common reason a buyer leaves. The page says the prices are provisional and that a signed client keeps the price they signed. Clear `provisional` and update the table in `docs/CLAIMS.md` once Alejandro sets the final numbers against Dexee's own costs.
24. **Guarantee terms are published as a reviewed-pending draft.** `/guarantee` states the replacement window (90 days, 120 for founding clients), the claim window, the response and shortlist commitments, five exclusions and the remedy, all from `GUARANTEE` in `src/content/pricing.ts`. Publishing terms a buyer's counsel can read before a call is worth more than keeping them in a contract nobody sees, but the page carries a notice that Dexee's counsel has not reviewed them and that the signed contract governs. The notice comes off only after that review; the checklist in `docs/CLAIMS.md` tracks it.
25. **The cost calculator computes the visitor's assumptions, not Dexee's measurements.** `src/lib/pricing/calculator.ts` is pure and runs in the browser; nothing is stored or sent. Every input, including the US and Colombian employer load percentages, is editable and the defaults are labelled as assumptions on the page. This keeps the calculator inside the claim-integrity rule from 9.0: the output is arithmetic on figures the visitor controls, so it makes no claim Dexee would have to source.
26. **`CALENDLY_URL` is optional and its buttons disappear without it.** The variable used to default to an invented URL. It is now `optionalString`, and `BookCallButton` returns `null` when it is unset, so no page ships a booking button that leads nowhere. Set the real link before the domain switch or leave the buttons off.
27. **The sample verification report is a worked example, not an anonymized real one.** PHASES-GTM 9.2 asks for a real, anonymized report. Dexee has not yet run a candidate through the platform, so there is nothing to anonymize; inventing one and presenting it as real would break the rule from 9.0. `/sample-report` renders `src/content/sample-report.ts` and says on the page that the figures were written to show the layout. The structure mirrors the product: the four oral rubric dimensions from `src/lib/assessments/english-oral.ts`, the CEFR scale from `cefr.ts` and the five IPIP factors from `workstyle.ts`. Phase 10.4 replaces the page with the product's own renderer over real seed data; delete `sample-report.ts` then rather than letting the two drift.
28. **Third-party evidence is stored once and rendered from messages.** `EVIDENCE` in `src/content/proof.ts` holds the id, publisher, date, link and the verbatim English statement; the text a visitor reads comes from `marketing.verify.evidence.<id>` so the Spanish page is in Spanish, as rule 4 of CLAUDE.md requires. `tests/unit/proof.test.ts` asserts the English message equals the record in `proof.ts` character for character, and that the Spanish message differs from it, so neither a reworded translation nor an untranslated copy passes the build.
29. **The marketing nav moves to the `xl` breakpoint and drops About.** Adding pricing and how-we-verify made seven top-level items, which pushed the logo out of the bar below 1280px. The six buyer-path links stay in the header from `xl` up and in the sheet menu below it; About keeps its footer link. The logo is `shrink-0` so a longer nav can never collapse it again.
30. **The buyer FAQ moves to semantic message keys and its own section.** `faq1Q`..`faq5A` are replaced by `marketing.companies.faq.<id>.{q,a}` with eleven entries, covering the nine topics PHASES-GTM 9.3 lists plus contact release and English verification. Numbered keys made it impossible to reorder or remove a question without renumbering the rest. The accordion moves out of the two-column pricing block into a full-width section, and `src/lib/seo/faq-page.ts` builds the `FAQPage` JSON-LD from the same strings the accordion renders, because Google drops the rich result when the markup and the visible page disagree. `tests/unit/faq-jsonld.test.ts` enforces the nine-question minimum, the 80-word limit per answer and key parity between locales.
31. **The lead is saved before anything else is attempted.** `createLead` inserts into `contact_requests` first and on its own. The acknowledgement email and the admin notification are queued afterwards and their failures are logged, never returned: a Resend or notification failure must not cost Dexee a lead the visitor has already been told arrived. PHASES-GTM 9.4 asks for one transaction path, and this is the version of that which fails safe rather than atomically discarding the lead.
32. **The response clock is one business day, not the doc's twenty-four business hours.** The form promises a written answer within one business day, so `src/lib/leads/response-time.ts` measures Monday-to-Friday 09:00-18:00 Bogotá and flags a lead once nine business hours have passed. Flagging at twenty-four business hours, roughly three working days, would let the queue look healthy while the published promise was already broken. Colombia has no daylight saving, so the UTC-5 offset is applied arithmetically rather than through a timezone database.
33. **`answered_at` and `answered_by` are stamped by the database, not the action.** `guard_contact_request_update` sets both when a lead moves to answered or converted, and refuses any non-admin update. The response-time report is only worth reading if it cannot be written around from the UI or by a stray service-role call.
34. **`npm run db:types` now runs the local generator.** The script pointed at `supabase gen types --linked`, which in an environment that cannot reach the project silently wrote an empty file over `src/types/database.ts`. The local PGlite generator produces the same shape from the migrations and cannot fail that way; the CLI version stays available as `npm run db:types:remote`.
35. **`allowedDevOrigins` is set for `next dev`.** Without it, Next blocks `/_next/hmr` over `127.0.0.1`, the client bundle never loads, and every form on the site falls back to a native GET submit. This was breaking the existing contact form too; it is a dev-only setting with no effect on the production build.
36. **A closed vacancy gets a page, not a 404.** `public_jobs_closed` is a narrow view — title, company, dates, nothing else — behind `/jobs/[slug]` when the role has left `public_jobs`. The page carries no `JobPosting` markup, sets `noindex, follow`, and offers the open roles in the same family. A bare 404 threw away every inbound link and left a visitor who followed a search result with nothing; Google accepts either, and this one is worth more. A slug that was never published still 404s, and a suspended company's jobs are excluded from the view entirely.
37. **The Indexing API is behind a credential and never fails a publish.** `src/lib/seo/indexing-api.ts` signs its own RS256 JWT with Web Crypto, so no dependency is added. Without `INDEXING_API_CREDENTIALS` every call is a silent no-op, and a failed ping is logged rather than returned: telling Google about a vacancy is not worth failing the action that published it. Publishing, approving, pausing and closing all ping.
38. **`buildAlternates` replaces twelve hand-written alternate blocks.** Every marketing page repeated the same canonical and languages object and none emitted `x-default`, so a search engine had no instruction for a visitor whose language Dexee does not publish. `x-default` points at English, which is what the buyer reads. The sitemap uses the absolute variant, since relative URLs are invalid there.
39. **Comparison pages concede in the frontmatter, and the test enforces it.** Each page in `content/compare/<locale>/` carries `bestAlternativeWhen`, rendered above the body rather than buried in it, and `tests/unit/compare-content.test.ts` fails a page whose concession is missing or too short to name a real scenario, and one whose headings never say where the alternative wins. PHASES-GTM 9.6 makes this the acceptance criterion because a comparison that concedes nothing reads as marketing. The frontmatter parser is twenty lines rather than a dependency: the format is ours, scalars only, and zod rejects anything unexpected.
40. **`remark-gfm` added for the comparison tables.** `MDXRemote` does not parse GitHub-flavoured tables by default, so the tables, which are the point of these pages, rendered as one run-on paragraph. The plugin is applied only on `/compare`; the legal pages have no tables. `.prose-dexee table` scrolls horizontally instead of overflowing on a phone.
41. **`dateOnly()` for dates that come from content, not from the database.** `new Date("2026-09-20")` is midnight UTC, which is the previous evening in `America/Bogota`, the app's configured timezone, so a page dated the 20th rendered as the 19th. Every date-only string now goes through `dateOnly()`, which anchors it at midday UTC. Timestamps read from Postgres are unaffected and stay as they were. This also fixed the same off-by-one on the legal pages' "updated" line.
42. **Nine analytics events, with the property allow-list in code.** `src/lib/analytics/events.ts` types the event names, so a typo is a build error rather than a metric that silently never appears, and `sanitizeProps` drops anything personal before it reaches a provider: known personal keys, any string over forty characters, anything containing an `@`. The events carry categories only — role family, seniority, budget band — never an id, a name or an email. `track()` is a no-op when no provider is loaded, which is every environment where `NEXT_PUBLIC_ANALYTICS_PROVIDER` is unset.
43. **`TrackView` guards against the double effect.** React strict mode runs effects twice in development, and PHASES-GTM 9.7 requires one event per action. The ref guard makes the page-view events fire once; `tests/e2e/events.spec.ts` asserts it by stubbing `window.plausible` before the page scripts run and counting.
44. **`tests/unit/messages-parity.test.ts` replaces a manual check.** Parity between `en.json` and `es.json` was held by hand and Phase 9 added several hundred keys; a missing key renders the raw key path on a live page. The test also enforces matching placeholders, no empty strings, the no-exclamation-marks and no-emoji rule from CLAUDE.md, and flags a Spanish string left identical to its English one. It caught the brand tagline, which stays in English by design and is listed as the one intentional exception.
45. **`PLAYWRIGHT_CHROMIUM_PATH` for environments with a pre-installed browser.** Playwright wanted a headless shell matching its pinned version, which this environment does not ship and cannot download. The config uses the binary at that path when the variable is set, and behaves as before when it is not.
46. **El proyecto remoto se migra con el MCP de Supabase, no con `supabase db push`.** Las versiones registradas en el proyecto alojado (identificador en las notas de entrega) no coinciden con los nombres de archivo de `supabase/migrations` (por ejemplo `20260901000001_enums.sql` quedó registrada como `20260918005317_enums`), porque cada migración se aplicó con `apply_migration` en el momento de provisionar. `supabase db push` vería esos archivos como pendientes e intentaría reaplicarlos, lo que falla en el primer `create type`. Para aplicar una migración nueva al proyecto remoto, use `apply_migration` con el contenido del archivo y el mismo nombre lógico, o alinee primero toda la tabla `supabase_migrations.schema_migrations`. `npm run db:verify` sigue siendo la verificación autoritativa del esquema, y no depende de esto.
47. **DISC se incorpora como cuarta prueba gratuita, revisando la decisión 17.** La decisión 17 descartó DISC porque la especificación había elegido IPIP Big Five. Alejandro pidió incluirlo en la Fase 10 y se añade sin reemplazar al Big Five: `supabase/seed/disc.json` contiene 28 ítems originales (siete por estilo, dos de ellos invertidos) escritos sobre el modelo de cuatro factores de Marston, que es de dominio público. El instrumento se llama "DISC" de forma genérica y nunca "DiSC(R)" ni "Everything DiSC", que son marcas registradas de Wiley; el descargo en `disc-copy.{en,es}.ts` lo dice en la página de resultados. La puntuación es determinista (`src/lib/assessments/disc.ts`): bruto 7–35 por estilo, escalado 0–100, estilo primario y secundario cuando la diferencia es menor de 15 puntos, con los mismos umbrales de banda que el Big Five. Como el perfil de trabajo, es contexto para una entrevista y nunca un filtro: la empresa no puede ordenar candidatos por estilo y el análisis de ajuste tiene instrucción explícita de no bajar la puntuación por ningún perfil.
48. **Los resultados vencen a los 90 días, todos por igual.** Alejandro dio un rango de 30 a 90 y pidió una recomendación. Se toma el máximo por tres razones: el nivel de inglés y los rasgos de personalidad cambian poco en tres meses, un plazo más corto obligaría al candidato a repetir pruebas en mitad de un proceso de selección, y 90 coincide con el `cooldown_days` ya vigente, así que un candidato nunca queda en la situación de tener un resultado vencido que todavía no puede repetir. `assessments.validity_days` (1–90) lo hace ajustable por prueba sin migración; el trigger `attempts_set_validity` sella `valid_until = validated_at + validity_days` en cada intento validado, y el índice sobre `(candidate_id, assessment_id, valid_until)` sostiene las consultas de vigencia.
49. **"Obligatorio" se aplica al postular, no al registrarse.** Las cuatro pruebas y la hoja de vida son requisito para enviar una postulación, no para crear la cuenta ni para ver vacantes. Bloquear el registro habría vaciado el embudo antes de que el candidato viera para qué sirven las pruebas. La regla vive en la base de datos: `applications_before_insert()` rechaza la inserción con `requirements_missing:<lista>` cuando falta algo, y la acción `applyToJob` consulta antes `candidate_apply_requirements()` para mostrar la lista de pendientes en lugar del error. Las postulaciones con `source = 'dexee_recommended'` y las que hace un administrador no pasan por el filtro, porque ahí Dexee ya evaluó al candidato.
50. **Los resultados vigentes entran solos al expediente de la vacante.** Cuando un candidato postula, la empresa ve en la tarjeta y en el cajón del pipeline el último resultado vigente de cada prueba, a través de `candidate_valid_results()`, que solo responde al propio candidato, a un administrador o a una empresa con `company_can_view_candidate`. Para que esto funcione con Big Five y DISC, el trigger de vigencia pone `visible_to_companies = true` en la primera validación de esos dos tipos; el candidato conserva los dos interruptores en Ajustes para retirarlo. Antes el valor por defecto era oculto, lo que habría dejado el expediente vacío justo cuando la prueba pasó a ser obligatoria.
51. **La hoja de vida se anonimiza antes de que la lea el modelo.** `src/lib/resume/redact.ts` elimina correos, teléfonos, URL y números de identificación, y descarta la línea completa cuando menciona fecha de nacimiento, edad, estado civil, religión, fotografía o similares, en inglés y en español, antes de que el texto llegue al análisis de ajuste. Así se cumple la regla 9 de CLAUDE.md también para datos que el candidato aporta él mismo en su PDF, y la regla 2, porque el contacto nunca sale del bucket privado hacia un tercero. La extracción de texto usa `unpdf` (1.8), que corre en Node sin dependencias nativas; los PDF escaneados sin capa de texto quedan registrados como `resume_unreadable` y el ajuste se calcula con el perfil.
52. **El análisis de ajuste es una recomendación, no una decisión.** `application_fit` guarda una puntuación 0–100, resumen, fortalezas, brechas y evidencia por dimensión, generada por Anthropic con el prompt versionado `candidate-fit.v1` y validada con zod. El panel de recomendados ordena por puntuación y marca top 3 y top 5, con los empates resueltos por orden de postulación. La empresa decide a quién entrevista; la puntuación nunca mueve una postulación de etapa ni oculta candidatos. Sin `ANTHROPIC_API_KEY` la fila queda en `skipped` con motivo `ai_unavailable` y el panel lo dice, en lugar de fallar la postulación. El cálculo corre tras la postulación con `after()`, se reintenta desde el cron `process-attempts` hasta tres veces, y se recalcula solo cuando cambia `inputs_hash` (vacante, perfil, hoja de vida o resultados).
53. **Se corrige una afirmación de la Fase 9.2 que no era cierta.** Las páginas `/how-we-verify` y `/sample-report` y el producto Dexee Verified describían una prueba de "competencias del rol" que la plataforma nunca tuvo. Se sustituye por lo que sí existe: perfiles de trabajo (Big Five y DISC) y análisis de ajuste sobre la hoja de vida. La corrección queda registrada en el log de `docs/CLAIMS.md`.
54. **DISC se despliega inactivo y se activa a mano.** La migración crea la fila de `assessments` con `is_active = false` porque el banco de preguntas no viaja en la migración. El procedimiento está en `docs/RUNBOOK.md`: cargar el banco y luego activar. Activar sin banco haría fallar `startAttempt` para todos los candidatos.
55. **El generador local de tipos no conoce el retorno de funciones de tabla.** `scripts/gen-types-local.ts` emite `Returns: unknown[]` para `candidate_apply_requirements` y `candidate_valid_results`, así que los servicios que las llaman por RPC declaran el tipo de fila y hacen la conversión en un solo punto. `npm run db:types:remote` produce el tipo correcto cuando hay proyecto enlazado.
56. **Los datos de demostración en producción se generan con las funciones de puntuación del producto.** `scripts/seed-demo.ts` construye los resultados de inglés, Big Five y DISC llamando a `scoreMcq`, `combineWrittenLevels`, `oralLevel`, `scoreWorkstyle`, `workstyleReport`, `scoreDisc` y `discReport` sobre respuestas sintéticas, de modo que los reportes almacenados tienen exactamente la forma que renderizan las páginas de resultado y el cajón de la empresa; un JSON escrito a mano se habría desalineado en la primera refactorización. Los análisis de ajuste sí son texto fijo, marcados `model = 'demo-seed'`, porque el servicio real depende de una clave de API y de una hoja de vida en el bucket, y ninguna de las dos existe para las cuentas demo. Todo lleva el prefijo `dd000000-`, el dominio `@demo.dexeegroup.com` y la palabra "demo" en títulos y resúmenes; `--cleanup` lo retira completo. La hoja de vida no se siembra: subirla es parte de la experiencia que el candidato demo debe vivir, y el bucket no es alcanzable desde el entorno de construcción.
57. **Las credenciales demo salen del repositorio y la contraseña anterior se da por quemada.** `scripts/seed-demo.ts` exportaba la contraseña de las seis cuentas demo y la documentación citaba el identificador del proyecto alojado; el repositorio estuvo público, así que esa combinación daba acceso como dueño de una empresa verificada. El script ahora exige `DEMO_SEED_PASSWORD` en el entorno y termina con instrucciones si falta; no hay valor por defecto. El valor anterior permanece en el historial de git, se considera comprometido de forma permanente y no debe reutilizarse en ningún entorno: las cuentas demo del proyecto alojado se rotaron a un valor nuevo el 2026-09-21 y ese valor vive solo en las notas de entrega. El identificador del proyecto se retira de `docs/` por la misma razón: solo, no abre nada, pero junto a una credencial filtrada acorta el camino.
58. **El JSON-LD se serializa con escapes unicode; los campos de texto viajan intactos.** `JSON.stringify` no toca `<`, así que un título con `</script>` cerraba la etiqueta y el resto corría como HTML en una página pública, con `unsafe-inline` en el CSP. `src/lib/seo/json-ld.ts` convierte `<`, `>`, `&` y los separadores U+2028/2029 a `\uXXXX`, que cualquier lector de JSON devuelve intacto; es el único control necesario y se aplica en los dos sinks (vacante y FAQ). La primera versión de esta corrección pasaba además `title`, `hiringOrganization.name` y `url` por `escapeHtml`; se revirtió en la fase D porque esos campos son texto plano en JSON-LD, no HTML, y Google mostraba `&amp;` literal en títulos como "AP & AR Specialist", frecuentes en la familia de finanzas que más vende Dexee. `description` sí se escapa, porque Google la interpreta como HTML. La prueba comprueba que la cadena serializada no contiene `</script>` y que el título parseado es idéntico al original, con `</script>` y con `&`.
59. **El contenido de una vacante se congela al salir de borrador; para corregirla se retira a borrador.** `patchJobDraft` leía el estado y no lo usaba, y ni la política ni el trigger distinguían estados, así que una empresa podía pasar la revisión con una vacante limpia y reescribirla publicada. Ahora `jobs_before_write` lanza `job_locked_for_edit` cuando un usuario no administrador cambia una columna de contenido con la vacante en `pending_review`, `published`, `paused` o `closed`; los cambios solo de estado siguen permitidos y los administradores no se ven afectados. Decisión de producto tomada para avanzar, pendiente de confirmación de Alejandro: la empresa corrige una vacante viva con una acción explícita que la devuelve a borrador (`changeJobStatus(..., "reopen")`), la vacante sale del tablero y del índice de Google mientras se edita, y el reenvío pasa por `submitJob`, es decir directo si la empresa está verificada y a `pending_review` si no. La alternativa considerada, mandar cualquier edición a `pending_review` sin retirarla, mantenía visible al público una versión que Dexee ya no había revisado. Las vacantes cerradas no se editan: se duplican.
60. **`dexee_only` oculta al candidato, y su postulación, a la empresa.** La columna `candidates.visibility` se escribía y nunca se leía en un camino de empresa, mientras la interfaz prometía lo contrario. La condición vive ahora dentro de `company_can_view_candidate()`, que es la puerta de todas las lecturas de empresa: `candidates`, `candidate_cards`, experiencia, educación, `candidate_valid_results`, `applications` y, desde esta fase, `application_fit`. `getVisibleWorkstyleBands`, que lee con rol de servicio, comprueba la visibilidad por su cuenta. Como la política de `applications` reutiliza la misma función, la postulación completa desaparece para la empresa, no solo el perfil; eso es lo que dice la promesa ("incluso cuando te postulas") y evita tarjetas anónimas que no llevan a nada. Decisión de producto tomada para avanzar, pendiente de confirmación: la postulación se acepta igual, el aviso de nueva postulación va a los administradores en lugar de la empresa, con enlace al candidato en el panel de administración, y Dexee intermedia: contacta al candidato, y si acepta, el candidato cambia su visibilidad o Dexee lo presenta como recomendado. La alternativa, bloquear la postulación en ese modo, dejaba al candidato sin poder mostrar interés sin exponer su perfil, que es justamente el caso de uso de la opción.
61. **Las empresas demo se marcan en la base y no salen a superficies públicas.** `scripts/seed-demo.ts` creaba una empresa `verified` con tres vacantes `published`, y `public_jobs` solo filtraba por estado: las vacantes ficticias aparecían en `/jobs`, en `sitemap.xml` y se anunciaban a la Indexing API, lo que viola las directrices de `JobPosting` de Google y permitía que un candidato real se postulara a un empleo inexistente. `companies.is_demo` (solo lo cambia un administrador; el guard de `companies` lo protege) excluye a la empresa de `public_jobs` y `public_jobs_closed`, con lo que el tablero y el sitemap la pierden sin tocar código, y `pingJobIndexing` (servicio compartido por la acción de empresa y la aprobación del administrador) no llama a Google para sus vacantes. Dentro de la sesión iniciada nada cambia: panel, pipeline, postulantes y ajuste siguen completos, porque esas lecturas pasan por RLS sobre las tablas y no por las vistas públicas. La alternativa, esconder las vacantes con un estado propio, habría roto el flujo que la demo quiere mostrar.
62. **`factor` no viaja al navegador.** Para Big Five y DISC la semilla escribe en `factor` el mismo valor que en `answer_key`, y el calificador lo usa como respaldo. La carga útil del intento omitía `answer_key` pero no `factor`, así que el candidato podía saber qué rasgo medía cada ítem y orientar su perfil, que las empresas ven como señal. `toPublicQuestion` (`src/lib/assessments/public-question.ts`) omite las dos columnas y la vista `assessment_questions_public` deja de exponer `factor`; los calificadores leen la tabla completa con rol de servicio, sin cambios. Las claves del inglés escrito ya estaban protegidas y no se tocaron.
63. **Toda página que lea con rol de servicio verifica el rol por sí misma.** La página de intentos del administrador era la única bajo `(app)` que usaba el cliente de servicio sin llamar a `requireRole`; dependía del proxy, que falla abierto cuando no encuentra el perfil. Ahora la verificación está en la página. Regla para adelante: el cliente de servicio en una página implica `requireRole` en esa misma página.
64. **Cambiar la contraseña exige la actual.** Una sesión robada bastaba para tomar la cuenta de forma permanente. La acción verifica la contraseña actual con un cliente de Auth sin sesión (para no tocar la del navegador), limita a cinco intentos por usuario cada quince minutos y devuelve un error específico al campo. `secure_password_change` queda activo en `supabase/config.toml` para el stack local; en el proyecto alojado es un ajuste del panel de Auth y debe activarse a mano (pendiente, anotado en RUNBOOK).
65. **El secreto de cron se compara en tiempo constante**, sobre resúmenes SHA-256 de ambos lados para que la longitud tampoco se filtre (`src/lib/constant-time.ts`).
66. **La IP para límites de tasa viene de la plataforma.** El primer valor de `x-forwarded-for` lo escribe el cliente, así que servía para evadir los límites de inicio de sesión, registro, recuperación, captación y contacto. `pickClientIp` usa primero `x-real-ip` (lo inyecta Vercel), luego `x-vercel-forwarded-for` y por último el último salto de `x-forwarded-for`, que añade el proxy. Límite conocido: sin `UPSTASH_REDIS_REST_URL` el contador vive en memoria del proceso y se reinicia con cada instancia y cada despliegue, así que en el plan actual el límite es una barrera contra abuso casual, no contra uno distribuido; configurar Upstash antes de abrir el registro a tráfico real.
67. **Las rutas de carga se validan por forma antes que por propiedad.** `companies/<propio>/../<otro>/logo.png` pasaba la comprobación de propiedad y se firmaba con `upsert`. `validateUploadPath` fija la profundidad exacta de cada bucket, rechaza `.` y `..` y exige UUID en el segmento de propietario; la ruta solo consulta la propiedad del id que la función devuelve.
68. **Las invitaciones de equipo caducan a los siete días.** `company_members.invite_expires_at` (valor por defecto en la base y fijado por la acción); las dos aceptaciones rechazan invitaciones vencidas, y las anteriores a la columna recibieron siete días desde la migración. Una invitación sin fecha se trata como vencida.
69. **El correo sale al encolarse; el cron es reintento.** Con el plan Hobby el outbox se vaciaba una vez al día, así que el acuse de un lead o una invitación podía tardar veintitrés horas. `deliver` programa `processOutbox(20)` con `after()` en la misma petición que encola, igual que ya hacía el inglés oral; la cerradura optimista por `attempts` evita envíos duplicados si el cron coincide. Fuera de una petición (scripts) `after()` no está disponible y el cron sigue siendo la vía.
70. **CI corre en la rama por defecto y la auditoría de dependencias bloquea.** El disparador apuntaba a `main`, que no existe en este repositorio, así que la suite solo corría por pull request; y `npm audit` tenía `continue-on-error`, con lo que una vulnerabilidad alta en producción no detenía nada.
71. **Los postulantes conservan su vacante y se enteran si cambian las condiciones.** Con la decisión 59, corregir una vacante viva la devuelve a borrador, y la lista de postulaciones del candidato leía la vacante desde `public_jobs`, que solo tiene publicadas: cada postulante veía un guion en lugar del título, como si la oferta hubiera desaparecido. `candidate_application_jobs()` (security definer, filtrada por `auth.uid()`) devuelve las vacantes detrás de las postulaciones propias con su estado, y la lista muestra "La empresa está actualizando esta vacante", "Pausada" o "Cerrada" en lugar del enlace. Además, al retirar a borrador una vacante con postulantes activos (no descartados, retirados ni contratados), la acción guarda en `jobs.reopen_snapshot` los ocho campos materiales: salario mínimo y máximo, tipo de contrato, tipo de empleo, seniority, nivel de inglés, modalidad y horas. Al reenviarla, `submitJob` compara y, si algo cambió, el evento `job_terms_changed` notifica a esos postulantes con el detalle en su idioma, por notificación y correo, recordándoles que pueden retirar la postulación. La confirmación de retirar muestra el número de postulantes activos. Se descartó avisar en cada guardado del asistente: el borrador cambia muchas veces antes de que la empresa lo reenvíe, y solo el resultado final importa al candidato.
72. **`NEXT_PUBLIC_SITE_URL` se normaliza en el esquema de entorno.** El valor configurado en Vercel llevaba barra final y cada unión `${siteUrl}/...` producía `//`: el sitemap entregaba a Google treinta URLs que las propias páginas declaraban no canónicas, y lo mismo iba a pasar con los hreflang absolutos, el `url` del JobPosting y las direcciones enviadas a la Indexing API. `env.ts` quita las barras finales antes de que cualquier consumidor lea el valor, así que la corrección no depende de cómo esté escrito en el panel; el valor debe ir igual sin barra, y tras el cambio de dominio hay que reenviar el sitemap en Search Console.
73. **La visibilidad "solo Dexee" también cubre el contacto liberado.** `company_can_view_contact()` seguía mirando solo `contact_released`, así que una empresa a la que Dexee ya había liberado el contacto conservaba correo, teléfono y enlaces aunque el candidato pasara a `dexee_only` y su perfil y postulación desaparecieran. La función exige ahora la misma condición de visibilidad que `company_can_view_candidate()`, y la aserción de la matriz incluye `candidate_contacts`. El archivo de la hoja de vida ya estaba cubierto porque su acción lee primero la postulación.
74. **Los bancos de evaluación salen del control de versiones.** El repositorio fue público y contenía las claves completas: 66 preguntas de inglés escrito con su respuesta correcta, 10 situacionales con la mejor opción, 12 consignas orales y los 28 ítems DISC con su estilo y su inversión. La regla 3 de CLAUDE.md y la corrección C1 protegen el navegador, pero cualquiera podía descargar las claves desde GitHub, y lo que Dexee vende es la verificación. Los bancos reales viven ahora solo en la base de datos de cada entorno y, como archivo fuente, en un directorio fuera del repositorio que el cargador lee de `ASSESSMENT_BANKS_DIR`. Sin esa variable, `scripts/seed.ts` y el cargador del demo terminan con un mensaje que explica qué falta; no hay caída silenciosa a un banco de ejemplo. Las pruebas y `db:verify` usan fijaciones evidentemente ficticias en `tests/fixtures/banks`, que cumplen la estructura y las cuotas pero no sirven como examen. `tests/unit/no-answer-keys.test.ts` falla si vuelve a versionarse un archivo con un campo `correct` o `best` fuera de las fijaciones. No se reescribió el historial de git: lo expuesto ya se clonó, reescribir habría roto los hashes de todas las ramas sin recuperar nada.
75. **IPIP-50 se queda en el repositorio; su secreto nunca fue alcanzable.** El International Personality Item Pool publica sus propios ítems y su clave, así que reservarlos no aporta nada. La mitigación del Big Five es la presentación, no el secreto: se muestra como perfil de estilo de trabajo, sin respuestas correctas, las empresas ven descriptores por banda y nunca ordena candidatos. Por eso la corrección C1, que retira la columna `factor` de la carga útil, no agrega protección real a este instrumento, aunque se aplique por igual. El mismo argumento vale para DISC, pero sus ítems son originales de Dexee y no públicos, así que se rotaron: la defensa en profundidad no cuesta nada cuando el contenido es propio.
